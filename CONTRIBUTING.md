# Contributing to N-AALP

Thank you for your interest in N-AALP, the Native Agentic Application Layer
Protocol. This repository hosts a protocol **specification** (an IETF
Internet-Draft) plus its reference implementations, conformance corpus, and IANA
registration material. N-AALP is the application layer carried by N-PAMP
(draft-bubblefish-npamp-01); the two are separate documents with separate
concerns. Contributions are welcome under the terms below.

## Ways to contribute

- **Report an issue** with the specification: an ambiguity, an inconsistency, a
  security concern, or an editorial problem. Open a GitHub issue and say plainly
  whether it is normative or editorial.
- **Propose a change** by opening a pull request against the draft source, an
  implementation, or the conformance corpus.

Please separate **normative** changes (anything that affects what an
implementation must do on the wire — object encoding, signed input, the channel
or carriage surfaces, the registries) from **editorial** changes (wording,
formatting, examples). Label them accordingly.

## Editing the draft

The prose specification is the Internet-Draft, maintained through the IETF Independent
Submission stream; contributions in this repository target the byte-level wire authority
`spec/naalp-draft-00.cddl`, the reference implementations, the conformance corpus, and the
docs. When you change the wire grammar:

1. Keep the source **ASCII-only**. Non-ASCII characters cause author-tool
   warnings; the only acceptable non-ASCII is what the renderer itself injects.
2. Render and lint locally:

   ```sh
   ./scripts/cddl_check.sh   # machine-validate spec/naalp-draft-00.cddl (RFC 8610)
   ```

   or use the hosted tools at <https://author-tools.ietf.org/>.

3. A pull request should leave the draft at **0 errors / 0 flaws** under idnits.

## How normative changes are decided

This document is offered through the IETF **Independent Submission** stream
(Informational category, pre-adoption). There is no working-group consensus
claimed for draft-00; the editor is a single, disclosed maintainer. Normative
changes are ultimately the responsibility of the document editor and, where
applicable, the Independent Submissions Editor and IETF review process. Opening
an issue or pull request is the right first step; acceptance of a normative
change is a deliberate editorial decision, not an automatic merge.

## How decisions are recorded (three layers)

N-AALP's value is a protocol whose every spec decision is **traceable**. The
decision history is maintained in three layers; all three are required for any
change that affects the protocol.

- **Layer 1 — Architecture Decision Records (the durable "why").** Every
  load-bearing decision (object-not-connection, post-quantum-first, effect-is-
  authorization, carriage-by-class, two-implementation byte parity) gets a
  numbered ADR in [`docs/adr/`](docs/adr/): `NNNN-verb-phrase-title.md`, with
  Status, Date, Context, Decision, and Consequences. Existing ADRs are
  superseded, not rewritten, and are part of the published documentation site.
- **Layer 2 — In-draft change log (the "what changed when").** Each draft
  revision adds a `## Changes Since draft-bubblefish-naalp-NN` subsection to the
  draft's change-log appendix. Git tags per revision + `rfcdiff` give the
  immutable per-revision timeline.
- **Layer 3 — Issue / PR labels (the discussion trail).** Label every issue
  `design` (substantive — affects the wire, even if the resolution is no change)
  or `editorial` (no substantive effect); add `has-consensus`,
  `needs-discussion`, or `proposal-ready` as applicable.

> Every `design`-labeled issue that reaches a resolution produces **(1)** a
> closing comment, **(2)** a numbered ADR in `docs/adr/` when it changed a
> load-bearing decision, and **(3)** a change-log bullet.

## Research and provenance discipline

Any claim about an external system (an RFC, a cipher, a library, a wire format)
is grounded in that system's **current published specification**, cited in the
ADR or the draft — never asserted from memory.

Conformance vectors are **never generated by the implementation they grade**;
that would be circular. Expected values are produced by independent Python
oracles in [`tools/`](tools/) anchored to the underlying standards — deterministic
CBOR (RFC 8949 §4.2.1), COSE_Sign1 (RFC 9052), ML-DSA-65/-87 (FIPS 204,
deterministic `rnd=0`), Ed25519 (RFC 8032), and NIST/FIPS known-answer vectors —
and the Go and Rust reference implementations are both cross-validated against
the **same** oracle bytes. A vector whose expected value came from the code under
test does not belong in the corpus.

## Code-point stability

The object encoding is intended to be stable within an object major version. The
byte-level authority is [`spec/naalp-draft-00.cddl`](spec/naalp-draft-00.cddl).
Additive registrations — a new channel surface, a new kind, a new carriage-class
identifier, a new signature or multicodec code point — are **value additions**
made through the IANA registries under their stated policies (Specification
Required / Expert Review / Experimental / Private Use), not layout changes.

Changes that alter the meaning of an existing object field, the deterministic
CBOR canonicalization, the signed-input construction, the content-id or signer-id
derivation, or the semantics of an already-assigned channel or kind are
**major-version** changes and will be treated as such (a new object version and,
if warranted, a new media type alongside `application/naalp+cbor`). N-AALP adds
no transport-dependent object guarantee: an object means the same thing over any
N-PAMP channel or any other transport.
